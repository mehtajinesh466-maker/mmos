### Sheet: 1. The Brief

| Siblings & Families — data brief for the new system |
| Master Moves Chess Club  |  prepared 05-Aug-2026  |  source: Zoho exports + acquirer settlement data |
|  |
| THE PROBLEM IN ONE LINE |
| Families are real in the business but do not exist in the data. Parents enrol several children, pay for them on ONE card, and expect one conversation — but every export we have is student-first, with no family, parent or payer entity anywhere in it. |
|  |
| HOW BIG IS IT |
| •  60 families identified, covering 130 students. |
| •  96 joint payments worth AED 421,641.00 — one card transaction covering 2, 3 or 4 children. |
| •  Those students hold 271 packages worth AED 541,880.90, which is 24.4% of all package revenue. |
| •  This is not an edge case. A quarter of the money arrives as a family payment. |
|  |
| WHAT BREAKS TODAY BECAUSE THERE IS NO FAMILY ENTITY |
| •  Reconciliation. One AED 7,875 swipe has to be matched to two package rows of 3,937 and 3,938. Nothing in the data says they belong together, so it can only be inferred by arithmetic. That inference took several passes to get right and still needed the owner to confirm 15 families by hand. |
| •  Revenue attribution. A sibling discount is applied to the family but recorded as a split across children, so per-student price looks wrong and no two siblings show the same rate. |
| •  Renewal and outreach. Front office calls the same parent twice, once per child, and cannot see that the family has one balance and one renewal date. |
| •  Refunds and credits. A credit belongs to the payer, not the child, and there is nowhere to hold it. |
| •  Attendance economics. Classes are consumed per child but paid per family, so per-child balances drift apart even when the family paid a single amount. |
|  |
| WHAT THIS WORKBOOK CONTAINS |
| •  2. Families — the 60 families we can evidence, with members, centres and value. |
| •  3. Joint Payments — all 96 payments where one card covered several children, with the exact split. |
| •  4. In Student Records — the export schema and what is missing for family grouping. |
| •  5. In Packages — the export schema and every sibling pattern seen in it, with real examples. |
| •  6. In Attendance — the export schema and what siblings imply for it. |
| •  7. Family Rollup — how the three sheets have to be added together per family, worked through on real data. |
| •  8. Proposed Data Model — tables and fields to build. |
| •  9. Detection Rules — how to infer families from the existing data at migration. |
| •  10. Test Cases — real families with the expected answer, to test the build against. |
|  |

### Sheet: 4. In Student Records

| How siblings appear in Student_records |
|  |
| One row per student. This is the master roster. There is NO family, parent, payer, household or guardian field of any kind. |
|  |
| THE EXPORT SCHEMA |
| Field | Sibling relevance | What the developer needs to know |
| Name | THE ONLY LINK | Free text. Siblings usually share a surname, but 11 of our 60 families do not. Case and spacing are inconsistent ("kian Lyndon", "TARA", "Bodhi  Chokdia" with a double space). |
| Student Id | unusable | Sparsely populated. It is not present at all in the Packages or Attendance exports, so it cannot be used to join. |
| Mobile/Whatsapp | BEST CANDIDATE | A parent number is normally shared by all their children. This is the strongest field available for inferring a family, but it is not enforced or validated today. |
| Date Enrolled | supporting | Siblings very often enrol on the same day. Useful as a secondary signal, not on its own. |
| Assigned center | watch out | Siblings can sit at DIFFERENT centres. We have 2 families split across Bay Avenue and JLT. Do not scope a family to one centre. |
| Age / Date of birth | supporting | Different per child, obviously, but a shared surname plus close ages plus the same phone number is a strong family signal. |
| School | supporting | Siblings usually share a school. Another weak signal to stack. |
| Status | watch out | One child can be Active while a sibling is Inactive. A family must survive its children changing status. |
| Overdue | recompute | System-calculated and known to drift. Never roll this up to a family; recompute from attendance. |
| Coaches Details, FIDE ID, Student category, Current Student levels, COUNTRY AS PER FIDE, ET /JLT Resident, Joining Student level, HOW DID YOU HEAR ABOUT US | no bearing | Per-child attributes. Nothing here groups a family. |
|  |
| THE GAP |
| Nothing in this export answers "who paid for this child" or "who else belongs to this family". Every family in tab 2 was reconstructed from PAYMENT behaviour, not from the roster. If the new system captures a payer at enrolment, this whole problem disappears. |


### Sheet: 5. In Packages

| How siblings appear in All_Student_Packages |
|  |
| One row per package purchased. This is where the damage is done: a single family payment is broken into one row per child, and the link between those rows is never recorded. |
|  |
| THE EXPORT SCHEMA |
| Field | Sibling relevance | What the developer needs to know |
| Student | the only link | Free text again, and must match Student_records exactly to join. There is no student id on this sheet. |
| Price | THE SPLIT | This is the child's SHARE of a family payment, not what was charged to the card. AED 7,875 on the card becomes 3,937 + 3,938 in Zoho. Nothing marks these two rows as one payment. |
| Date of payment | unreliable for grouping | Siblings on ONE card can carry DIFFERENT Zoho dates. We have 9 groups like this — the Bajaj children are dated 12 and 17 Dec against a single swipe on the 17th. |
| Mode of payment | unreliable | Frequently blank or wrong. Two rows we chased were only resolved when the owner confirmed the mode was never filled in. |
| Assigned center | watch out | A family payment can cover children at both centres. One AED 5,355 swipe covered two Bay Avenue children and two JLT children. |
| No of classes | per child | Each child gets their own class count. Siblings on one payment often get DIFFERENT counts, so you cannot derive the split from classes either. |
| New/Renewal, Class Status | per child | Independent per child. One sibling can be renewing while the other is new. |
| Completed Classes, Overdue | do not trust | System-calculated and known to drift from actual attendance. Recompute from attendance records. |
| Student Enroll First | supporting | Siblings usually share an enrolment date. |
|  |
| EVERY SPLIT PATTERN WE FOUND, AND HOW OFTEN |
| Pattern | Groups | What it means for the model |
| Even split, exact | 84 | The simple case. Card amount equals the sum of the child prices to the fill. |
| Uneven split | 6 | Children on one payment get DIFFERENT amounts. Do not assume equal shares. |
| Rounding, off by AED 1-5 | 8 | 3,937 + 3,938 = 7,875. An exact-sum test fails. Allow a small tolerance, or better, stop splitting at all. |
| Card carries 5% VAT on top | 1 | Zoho 960 x 3 = 2,880 settled as a 3,024 swipe. Store the gross charged AND the net booked. |
| Zoho dates differ across children | 9 | The payment date on the child row is when it was keyed, not when the card was charged. Store the real transaction datetime. |
| 3 children on one payment | 6 | Groups are not always pairs. |
| 4 children on one payment | 3 | Model N children per payment, not two. |
| Cross-centre family payment | 5 | A family is not owned by a centre. Do not scope the family entity to a branch. |
| Unexplained variance | 3 | Discount or fee applied at family level and not carried onto the child rows. |
|  |
| WORKED EXAMPLE — one card, two rows, no link |
| Card transaction | 22-Jul-2026 | Mashreq POS terminal | AED 7,875.00 | one swipe |


### Sheet: 6. In Attendance

| How siblings appear in All_Attendance_Records |
|  |
| One row per class session, per child. Attendance is genuinely individual — this is the one place where per-child data is correct and should stay that way. |
|  |
| THE EXPORT SCHEMA |
| Field | Sibling relevance | What the developer needs to know |
| Student | the only link | Same free-text join problem. No student id on this sheet either. |
| Date, Session time | per child | Siblings often attend the SAME session — useful as a family signal, but never merge their attendance. |
| Attendance | normalise first | Values are inconsistently cased and worded: Present, present, Absent, "Absent but informed". Count a session only on a case-insensitive match to "present". |
| Assigned center | watch out | A child attends at their own centre even when the family paid through the other one. |
| Coaches Details, Class duration, Auto sync, ID | no bearing | Per-session attributes. |
|  |
| THE RULE THAT MATTERS |
| •  Attendance stays PER CHILD. Classes are consumed by the child who sat in the room. |
| •  Money is FAMILY level. Classes are CHILD level. Keep them in separate tables and join them through the child. |
| •  Do not net a family balance in classes. Two siblings can buy 24 classes each on one payment and burn them at completely different rates — the family owes nothing but one child may be out of classes. |
| •  Consume attendance against that child's own packages in date order, exactly as the existing overdue logic does. The family payment does not change that; it only changes how the package was funded. |


### Sheet: 7. Family Rollup

| Family Rollup — how the three sheets add together |
|  |
| What rolls UP to the family, what stays DOWN at the child, and what must never be netted. Get this wrong and either the parent is billed twice or a child attends classes nobody paid for. |
|  |
| THE RULE TABLE |
| Measure | Lives at | Rolls up? | How to compute | Trap |
| Amount charged | FAMILY / payment | n/a | The gross on the card. One row per real card transaction. | Never reconstruct it by summing child prices — rounding and discounts make that fail. |
| Allocation to a child | link table | n/a | payment_id -> student_id -> allocated amount. Must sum to the payment gross. | Enforce the sum with a constraint. That single check would have caught every case in tab 3. |
| Discount | FAMILY | yes | Applied to the payment, then allocated. Store the reason. | Today it is silently buried in the child split, so per-child price looks arbitrary. |
| Classes purchased | CHILD | no | Per child, on their own package. | Siblings on one payment often buy different class counts. |
| Classes attended | CHILD | no | Count attendance rows matching "present", case-insensitive. | Never merge siblings' attendance, even when they sit in the same session. |
| Classes remaining | CHILD | no | Consume that child's attendance against that child's packages in date order. | Do not net across siblings. One child can be out of classes while the family is in credit. |
| Amount owed / credit | FAMILY | yes | Sum of family payments less the value of what each child has consumed. | A credit belongs to the payer, not the child. It must survive one child leaving. |
| Renewal due date | FAMILY view, CHILD source | yes | Earliest renewal across the children, surfaced as one family action. | Front office should get ONE call to make, not one per child. |
| Centre | CHILD | no | Each child sits at their own centre. | A family is not owned by a centre. 2 of our families span both. |
| Contact / payer | FAMILY | yes | One payer record, one phone, one email. | This is the field that does not exist today and causes everything else. |
|  |
| WORKED EXAMPLE — the Bajaj family, 17-Dec-2025 |
| Step | Source sheet | Value | Note |
| One card swipe | acquirer settlement | AED 3,024.00 | the only true record of what was charged |
| Zoho: Rudra Bajaj | Packages | AED 960.00 | dated 17-Dec |
| Zoho: Shiva Bajaj | Packages | AED 960.00 | dated 12-Dec — five days earlier than the swipe |
| Zoho: Veer Bajaj | Packages | AED 960.00 | dated 17-Dec |
| Sum of the three |  | AED 2,880.00 | AED 144 short of the card |
| Why |  | x 1.05 | the card carried 5% VAT: 2,880 x 1.05 = 3,024 exactly |
| Family owes |  | nil | one payment, fully allocated |
| Each child's classes | Attendance | independent | consumed separately, at their own pace |


### Sheet: 8. Proposed Data Model

| Proposed data model |
|  |
| Five tables. The important move is that a payment is recorded once, at family level, and allocated to children through a link table — rather than being pre-split onto the child rows as it is today. |
|  |
| Table | Field | Type / key | Why |
| family | family_id | PK | One household. |
|  | display_name | text | e.g. "Bajaj". Free text, for the front office only — never used as a key. |
|  | primary_payer_id | FK payer | Who normally pays. |
|  | notes | text |
| payer | payer_id | PK | A parent or guardian. Separate from family because a family can have two payers, and a payer can pay for more than one family. |
|  | name, mobile, email | text | Mobile is the field that would have let us group every family in tab 2 automatically. |
| student | student_id | PK | One child. Keep the existing roster fields. |
|  | family_id | FK family, NULLABLE | Nullable on purpose — a child with no siblings needs no family, and forcing one creates noise. |
|  | centre_id | FK | Per child. NOT inherited from the family. |
| payment | payment_id | PK | ONE row per real card transaction. This is the row that was missing. |
|  | family_id | FK family | Who the payment is for. |
|  | payer_id | FK payer | Who actually paid. |
|  | gross_amount | decimal | What hit the card, VAT included. |
|  | net_amount | decimal | What settled to the bank after acquirer fees. |
|  | discount_amount, discount_reason | decimal, text | Family-level. Stop burying it in the child split. |
|  | channel, terminal_id, acquirer_ref, card_last4 | text | Enough to tie back to the settlement file without guessing. |
|  | transacted_at | datetime | The REAL card timestamp, not the date somebody keyed the record. |
| package | package_id | PK | One purchase for one child. |
|  | student_id | FK student | Per child. |
|  | classes_purchased, price_allocated | int, decimal | price_allocated is this child's SHARE of the payment. |
| payment_allocation | payment_id, package_id | composite PK | THE LINK THAT DOES NOT EXIST TODAY. |
|  | allocated_amount | decimal | CONSTRAINT: sum of allocated_amount per payment_id = payment.gross_amount. This one constraint prevents every problem in tab 3. |
| attendance | attendance_id, student_id, session_datetime, status |  | Unchanged. Per child, always. |


### Sheet: 9. Detection Rules

| Migration — how to infer families from the existing data |
|  |
| This is the exact ladder used to build tab 2. Run it in order and stop at the first rule that fires. Anything that reaches the bottom needs a human. |
|  |
| Rule | Test | Confidence | Notes |
| 1 | Two or more packages whose prices sum EXACTLY to one card transaction, within 3 days | CERTAIN | Fired 84 times. This is the backbone. |
| 2 | Same as rule 1 but allow AED 5 tolerance | CERTAIN | Fired 8 times. Catches the 3,937 + 3,938 = 7,875 split. |
| 3 | Same as rule 1 but test sum x 1.05 as well | CERTAIN | Fired 0 time. Catches VAT added on the card. |
| 4 | Widen the date window to 14 days before matching | HIGH | Zoho dates drift from the swipe date on 9 groups. |
| 5 | The payment reference names two students ("MAYA&LUNA", "AARYA/DARSH") | HIGH | noon references carry names. Free, and independent of the amount. |
| 6 | Shared surname AND overlapping enrolment | MEDIUM | Fails on the 11 families with different surnames — do not rely on it alone. |
| 7 | Shared parent mobile number | SHOULD BE HIGHEST | Not usable on the current export, but this is what the new system should capture. It would replace rules 1 to 6. |
| 8 | Anything left | ASK | 15 families needed the owner to confirm by hand. Budget for a review screen; do not auto-merge on a guess. |
|  |
| THINGS THAT WILL BITE YOU |
| •  Do not merge on surname alone. "Bodhi Chokdia" pays with "Amit Chordia" and "Vanya Chordia" — three different spellings, one payment. |
| •  Do not assume pairs. 6 groups have 3 children and 3 have 4. |
| •  Do not assume equal shares. 6 groups are split unevenly. |
| •  Do not scope a family to a centre. 2 families span both. |
| •  Names have double spaces, mixed case and misspellings between sheets ("Noan"/"Noah Dukhgan", "Ayub Elmi"/"Ayub Elimi"). Normalise before joining. |
| •  Exact-duplicate package rows exist. We found Oliver Heebarth entered twice for the same AED 840. De-duplicate before you infer anything. |
